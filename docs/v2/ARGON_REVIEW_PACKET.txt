  have an uncertain billed outcome. Promise reduced duplicate work, not zero waste.
- SHA-256 addresses immutable blobs, not mutable artifact identity. Separate
  records, versions, blobs, references and many-to-many lineage. Scorecards need
  evaluator authority; an agent artifact cannot self-certify official metrics.
- A single `is_apex` column does not enforce one current Apex or explain a Pareto
  set. Use a revisioned project selection record pointing to a verified candidate.
- A new local HTTP service needs authentication, project authorization, safe
  rendering and cursor replay. Loopback binding alone does not supply these.
- Hidden validation labels do not prevent repeated-score overfitting or leakage
  through detailed residuals. Budget adaptive submissions and diagnostics; preserve
  an untouched final test. Data agents may inspect training labels, not raw sealed
  evaluation residuals that reconstruct labels.
- A 128 MiB total-state ceiling conflicts with large weights/runtime assets and
  permanent retry fences. Enforce the current policy first; design explicit
  separate control-state, artifact, environment and export budgets before expansion.
- Ten projects with five scripts each means 50 queued/runnable intents. Fifty
  simultaneously running jobs are conditional on admitted resource demand. Memory
  limits are caps, not reservations of physical RAM; summed demands are a planning
  risk, not proof that container limits allocate 50 GiB immediately.
- Reserve host/VM capacity by measured capabilities and configurable headroom;
  fixed “2 cores + 2 GiB” is unsuitable for every device. Docker's Linux VM budget
  can be lower than macOS host RAM. MPS on the host is not exposed merely because
  Apple Silicon exists.
- CPU thread settings already exist in one path; apply them to all backends.
  Fractional CPU quotas still require at least one library thread and are not an
  integer thread allocation. Required resource claims need measurement provenance.
- Context limits include schemas, message overhead and response allowance. Bytes/4
  is not a hard token guarantee. Compaction must preserve tool-call/result pairs,
  latest steering and pending actions, not merely the earliest 300 request characters.
- Three seeds are configurable repeated runs, not an automatic confidence interval
  or proof of generalization. Choose confirmation protocols by task and budget.
- A formula cannot return an exact GPU-hour deficit. Use bounded pilots and report
  estimate ranges, confidence and assumptions. Unsupervised internal metrics and
  offline RL OPE cannot universally certify downstream usefulness or policy safety.

**Defer:** warm zygote workers, broad remote execution, RL and small-LLM training
until the corresponding capability and scientific acceptance gates pass. Shared
containers enlarge the isolation problem; a child directory and privilege drop
do not establish per-job namespace, process or memory separation.

## External design checks

The following primary sources informed these corrections, accessed 2026-10-14:

- Python 3.13 warns that mixing threads with `fork()` is unsafe. A preloaded
  scientific-library daemon therefore needs a dedicated compatibility experiment:
  [Python os.fork documentation](https://docs.python.org/3.13/library/os.html#os.fork).
- Cgroup `memory.max` is enforcement; `memory.peak` is measurement of the cgroup
  and descendants. A shared container's lifetime peak is not a job-specific
  certificate. Kernel/version/reset support must be checked:
  [Linux cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html).
- WAL allows reader/writer concurrency, but long readers can prevent checkpoint
  completion and grow WAL files. Bound read transactions and size the pool from
  measured load rather than hardcoding 16 connections:
  [SQLite WAL documentation](https://www.sqlite.org/wal.html).

parity and declared limitations. Unsupported task types remain rejected.

## Recommendation priority

Ship model rescue and transparent evidence first; they distinguish the product
without needing exotic ML. Next add reproducible environment profiles, better
diagnostics and compute estimates. Add out-of-core/time-series/frozen embeddings
before small-LLM/RL ambitions. Benchmark MCTS, warm pools and DB sharding as optional
optimizations; do not make them prerequisites for a useful tabular coding harness.

# Target architecture and contract requirements

Status: proposed implementation contracts, 2026-10-14. Names below are design
targets, not existing commands or generated schemas. Implement versioned schemas
and cross-language fixtures in the phase that owns each contract.

Contract ownership includes `contracts/v1/`, `scripts/generate_contracts.py`,
`crates/harness/src/contracts.rs` and the Python protocol validators. The existing
generator writes the v1 worker frame schema and fixture corpus; it does not generate
every Rust type or scientific schema. Extend generation/checking for new contracts
under an explicit version (for example `contracts/v2/`) without rewriting v1 meaning.
Change worker frames only when transport semantics require it, and keep supported
old frames/fixtures stable through the compatibility window.

## Ownership and flow

```mermaid
flowchart TD
    U[User: problem, data, existing code, constraints] --> I[Intake and feasibility plan]
    I --> O[Lead agent and durable task graph]
    O --> T[Generic tool gateway]
    T --> B[Global resource lease broker]
    B --> S[Isolated candidate jobs]
    S --> E[Trusted evaluator and benchmark runner]
    E --> A[Candidate evidence and Apex selection]
    A --> V[Independent verifier and critic]
    V --> F[Frozen finalization and sealed test]
    F --> D[Standalone deployable bundle]
    T --> R[Artifact registry and event journal]
    E --> R
    R --> UI[Authenticated local dashboard]
    UI --> C[Revisioned user commands and notes]
    C --> O
```

Rust owns identity, authorization, lifecycle, admission, budgets, durable receipts,
artifact publication, official-result registration, event ordering and delivery
gates. Python owns data/ML computation and evaluator implementations in an isolated
trusted evaluator scope. Candidate code never shares label access or mutation
authority with that evaluator. Agents own hypotheses and code choices; their
claims remain proposals until deterministic checks accept their evidence.

“Deterministic” applies to state transitions, input binding, receipts and admission.
Model training/LLM reasoning may vary; record seeds, environment/device identities
and numerical tolerances. Identical hashes do not promise cross-device equality.

## Artifact registry

Use additive migrations and retain M6 scientific records during transition.

The existing 128 MiB policy covers managed state, not just SQLite/control metadata.
P1 first enforces that policy across all covered writes. A proposed versioned policy
then introduces separate control-state, artifact CAS, staging/export and environment
quotas at project/global scope, with shared device disk limits and recovery headroom.
Explicitly migrate accounting and limits before placing large weights outside the
old cap. Merely renaming the old ceiling `control_state_bytes` is not preservation.

| Entity | Required data and responsibility |
| --- | --- |
| Blob | SHA-256, verified bytes, owned CAS path, media type; immutable content |
| Artifact | Project-scoped logical ID, kind, producer identity/authority, current version, pins, visibility, tombstone |
| Artifact version | Immutable version ID, blob reference, compact index digest, bounded detailed summary, schema version, source/environment/job bindings |
| Lineage edge | Project-scoped source/destination version IDs and relation: derived_from, evaluates, packages, supersedes |
| Annotation | User/agent note, author, revision, referenced artifact version; never edits an official score |
| Selection | Project revision, candidate and scorecard version, protocol, rationale; unique current Apex pointer |
| Event | Monotonic cursor, project, type/version, committed revision and bounded payload/reference |

Kinds initially cover data profiles, research notes, code, run logs/curves,
diagnostic specs, predictions, scorecards and Apex bundles. Validate payloads with
versioned kind schemas; keep extensions namespaced rather than another permanent
SQL enum bottleneck. Directory artifacts use canonical manifests of file hashes;
validate paths, symlinks, file count and aggregate size before committing.

CRUD means create immutable version, read/query/lineage, update annotations or
publish successor version, and tombstone an unprotected record. Delete never
rewrites lineage, score history, consumed assessments or retry fences. Pinning
controls retention; baseline designation controls comparison; neither crowns Apex.

Publication protocol: acquire byte reservation -> write bounded staging -> hash
and fsync -> atomically publish owned bytes -> commit registry plus event -> settle
reservation. Filesystem and SQLite are not one transaction: reconcile staged files,
orphan blobs and incomplete publication receipts on restart. GC marks references
and leases, tombstones, deletes owned unreferenced bytes, then records completion.
Cross-project deduplication must not expose another project's data or retention.

Agents and UI use the same command service. Official scorecards are writeable only
by evaluator authority; claimed agent metrics are explicitly unofficial. Queries
are paginated, summaries default to <=4 KiB, and raw logs require explicit bounded
retrieval. Privacy/redaction policy applies before notes/plots enter provider views.

List/leaderboard/context injection uses a proposed `index_digest` <=512 UTF-8 bytes;
detailed `summary_text` <=4 KiB is fetched on demand. Bytes are storage bounds, not
token guarantees: measure tokens and cap total query output separately. Apply
typed outbound projection, approved-view policy and `gateway.rs::OutboundFilter`
before provider dispatch. The current heuristic filter cannot guarantee removal of
all secrets/private records. Bind prompt approval, hashing and accounting to the
actual serialized outbound payload; validate tool JSON and required state after
sanitization so truncation/redaction cannot corrupt tool-call history silently.

## Coding tools and candidate boundary

Expose four versioned tool families, backed by existing operations where possible:

| Tool | Contract |
| --- | --- |
| `workspace_fs` | Scoped read/write/patch/glob/search; expected content hash for mutations; bounded results; reject path and symlink escapes |
| `sandbox_exec` | Prefer structured argv; explicit shell mode for agent scripts; approved environment, task generation, lease, deadline, output/scratch caps, durable receipt |
| `evaluate_submission` | Register candidate and bound prediction artifact; locked metric/split; trusted validation and benchmark receipts; adaptive-query budget |
| `artifact_crud` | Project-scoped publication/query/version/lineage/pin/tombstone; expected revision and reservation; no official-score forgery |

Keep governed orchestration controls: delegate, inspect status, complete subtask,
pause/cancel/resume, steering and request finalization. No sandbox tool may run
directly without a broker lease. Retain registered project tools as optional
reusable descriptors calling the same gateway rather than an independent runner.

Candidate v2 is an executable directory plus manifest. The manifest binds source,
training environment, inference environment, input/output schemas, task type,
supported operations, seeds and declared resource request. Example target:

```text
candidate/manifest.json
candidate/entrypoint.py
candidate/source/...
training.lock
inference.lock
```

```sh
python -m candidate.entrypoint fit --train-path /inputs/train.csv --model-dir /outputs/model
python -m candidate.entrypoint predict --input-path /inputs/features.csv --model-dir /inputs/model --output-path /outputs/predictions.csv
```

The harness provides immutable fit data, feature-only prediction inputs, stable row
IDs and class order. Predictions must bind row IDs, candidate/source/model hash,
split fingerprint and protocol; reject missing/extra/duplicate rows, bad dimensions,
NaNs, invalid probabilities and class-order mismatches. Prediction fit state and
official benchmarks refer to the same immutable candidate/model bytes.

Mount only one task's scoped inputs, source and outputs; never mount shared state,
evaluator labels, other branches, credentials or Docker socket. Export changes
through validated publication. Legacy models and pickle files are untrusted code;
inspect/load only inside the candidate sandbox. No runtime `pip install`: approved
locked environments are prepared as separately budgeted jobs before offline fitting.

Default execution uses immutable `/workspace:ro` and task-specific bounded
`/scratch:rw` and `/outputs:rw`; source mutations go through `workspace_fs`.
An explicit staged writable workspace/overlay is optional, with its diff validated
before commit to the branch. Candidate development and official prediction use
the same approved digest-pinned training profile; a distinct inference profile
must be bound and verified for delivery. A read-only mount alone does not authorize
retry: prior publication, evaluator queries, persistent caches and surviving
containers still require reconciliation before resetting disposable output.

Harness-owned CV execution freezes source/config and materializes only each fold's
training rows/labels plus feature-only held-out rows for isolated fit/predict jobs.
Do not mount every fold's training directory together: other folds contain this
fold's held-out labels. Carry only that fold's verified fit artifact to prediction;
block cross-fold writable caches and reused trained weights. Independent scoring
checks row/model/source/split identity and produces authoritative OOF provenance.

The coding agent may already have inspected the full development training labels.
Per-fold mounts prevent accidental shared preprocessing and direct held-label reads
in each run; they cannot prove an agent did not encode remembered labels in source.
Record label exposure and review source/data provenance. Treat development OOF
results accordingly; untouched outer validation/final-test boundaries remain needed
for independent assessment. Newly exposed holdouts are not retroactively independent.

Calibration consumes row/class-aligned OOF prediction tables and training labels;
ensembles use verified parent prediction/model manifests instead of importing their
code into the label-bearing evaluator. Keep composite inference isolated and count
all parent costs. Stacking/calibration training data is distinct from evaluation:
use separate outer validation or properly nested cross-fitting, never report scores
on labels used to fit the combiner as independent evidence. Extend recipe-specific
`scheduled_pipeline.py` and `search/adapter.py` with candidate prediction/search-space
adapters; `calibration.py` already accepts OOF arrays and need not become a universal
estimator class.

Returned validation diagnostics enforce configurable minimum slice support,
coarsening and a shared query budget. Count overlapping/adaptive queries, fidelity
levels and duplicate submissions according to the locked protocol. A minimum group
size alone does not prevent differencing attacks or guarantee privacy; never expose
row-level sealed residuals, and bound the total diagnostic information released.

Rescue distinguishes repaired unfitted source from a supplied pretrained artifact.
A pretrained baseline defaults to `unverified_legacy_baseline` until training/data
provenance supports assessment on an untouched disjoint holdout. Clean refit rebuilds
preprocessing, learned state and weights from permitted training rows; warm-starting
old weights is not a clean refit. User attestations are recorded with uncertainty,
not treated as cryptographic proof of disjointness. If evaluation rows were already
used for development, refitting does not restore their independent-test status.

## Resource broker and execution

Lease fields: project/task/job, generation, backend and device, CPU millicores,
library threads, memory limit/reservation, accelerator units/bytes where supported,
scratch/output bytes, PID cap, deadline, heartbeat and environment hash. Persist
reserve/start/finish/reconcile transitions; terminate and reap before release.

Label Docker containers with harness/state-root owner identity, project, lease and
generation, and persist the exact container ID. Startup discovers daemon-side
survivors even when the CLI client died. Verify ownership and current lease epoch
before adopting or terminating a survivor; do not blindly kill every labeled
container, as another live supervisor may own it. Collect terminal telemetry,
confirm container removal/descendant exit and only then release its reservation.

Use capacity accounting for instantaneous CPU/RAM/GPU/storage and cumulative
accounting for time/tokens/cost. Start with weighted fair queues, per-project limits
and aging; add dominant-resource fairness only when multi-resource traces justify
its complexity. Suspend new admissions under pressure. Do not kill a training job
for fairness unless it explicitly supports resumable checkpoint/preemption.

Available capacity is the constrained runner/device budget minus configurable
headroom, warm-worker overhead and active reservations. Docker VM limits matter on
macOS. MICRO/STANDARD/HEAVY are configurable request presets, not universal truth.
Fractional CPU jobs normally use one library thread; integral leases cap BLAS,
OpenMP, Polars and estimator-specific jobs. Nested CV/HPO parallelism shares the
same allocation. Fifty jobs can queue; actual dispatch satisfies aggregate limits.

Backend capability reports distinguish enforcement, telemetry and certification.
Record per-job memory.max/peak/events and measurement scope on supported Linux
cgroups. An OOM is a failed trial; missing measurements cannot pass a required
constraint. Training peak, inference peak and warm worker overhead are separate.
Metrics collector is trusted and candidate-write-protected. Initially retain
one disposable container per job; pooling is a later measured optimization.

## Durable agents, recovery and memory

Default roles: lead, data/diagnostics, experiment engineer, independent verifier,
critic. Estimator combines deterministic hardware/pilot evidence with agent task
interpretation. Specialist roles are capabilities, not five always-running LLMs.
Keep deterministic verifier separate from an advisory/binding-policy critic.

Task contract: goal, falsifiable hypothesis, immutable inputs, allowed tools,
branch ownership, limits, expected artifacts, acceptance criteria and dependency
IDs. Completion receipt: verdict, experiment/candidate/source IDs, measured metric
delta and protocol, failures, bounded learnings and next actions. Enforce receipt
schema before updating the lead's memory. Invoke research/critic specialists only
when uncertainty or a milestone justifies their cost. External research requires
approved egress and content provenance; training remains offline.

Provider turn ledger binds canonical request, model/settings, prompt/policy/tool
versions, dispatch identity, raw response and usage settlement. Persist the response
before executing tools. Crash before response persistence may leave unknown billing;
reconcile provider evidence when available and refuse to claim exactly-once billing.

Classify tools: pure read, transactional command, isolated replayable job,
reconcilable external operation, irreversible operation. Store intent before effects
and result before context update. Unknown outcomes reconcile using job/command/blob
receipts; never reset-and-replay arbitrary shell effects. Finalization stays tied
to its original frozen artifact; exposed assessment cannot be recreated by retry.

Pause stops admission and checkpoints at a safe boundary. Cancel fences tasks and
terminates descendants; restart discovers surviving containers/processes and leases.
Resume loads authoritative state and the unfinished operation, not a reconstructed
conversation guess. Latest steering changes intent revision and invalidates stale
worker proposals. Lost workers, paused projects and failed projects remain distinct.

Context policy: default approximately 16K total window when supported; maximum
64,000 or provider's smaller window. Count system/messages/schemas/tool results plus
response allowance. Suggested upper-window allocations: 4K pinned state, 12K bounded
milestone summaries, 32K active work, 8K response, 8K schemas/overhead/safety margin.
Unused portions are optional capacity, not required padding. Trigger compaction
before the next request exceeds its budget. Use exact tokenizer where available;
otherwise a conservative bound and an explicit unsupported hard-guarantee report.

Preserve full constraints, newest user steering, Apex/protocol identity, current
leases/tool pairs, unresolved failures and final-test status. Full logs live in
artifacts; provide bounded excerpts and IDs. Summaries are cached with input hashes,
versioned and recoverable; they are never official scientific evidence.

## API and transparent dashboard

Serve loopback Rust API and static UI. Preserve authentication, Host/Origin checks,
CSRF protection for cookie-authenticated mutations, expected revision and idempotent
command IDs. Reuse current `/v1` contracts or add explicit version negotiation;
avoid an accidental `/api/v1` break. Stream durable events after commit with SSE
cursor IDs and Last-Event-ID replay. Snapshot includes revision and cursor; expired
cursors trigger a new snapshot. Disconnect slow readers without blocking writers.
Transient telemetry can be coalesced; terminal state/selection events remain durable.

Five views: experiment DAG with actual running/pruned/failure states; leaderboard
with feasibility and Pareto alternatives; data/model diagnostics with sample counts
and provenance; research feed with hypothesis, evidence and critic notes; resource
drawer with allocated/measured CPU/RAM, leases, queue waits and backend capacity. Queued,
running, screening, validated and final verified states must be visually distinct.
Animation follows receipts, never invents progress or hides waiting for resources.
Use accessible status text, reduced-motion support, virtualization and safe markdown
rendering. Treat plot specs as data; reject executable JS/HTML and remote loads.

User notes/edits become revisioned artifacts/commands. Agents receive a bounded
steering delta at safe boundaries. Downloads verify authorization and immutable
manifest identity. Readers use bounded snapshots/transactions, not a transaction
held open for the lifetime of an SSE connection.

## Delivery and expansion

Freeze candidate, environment, selection and approvals; refit within reserved budget;
reload and certify the exact pipeline; consume sealed test once; package matching
weights, inference CLI/API, schemas, locks, training source, scorecard, model card,
lineage and verification receipts. An optional container/service recipe follows;
live hosting is separately authorized. No final verified label for missing evidence.

TaskAdapter specifies input/schema/split protocol, fit/predict/evaluate operations,
constraints and packaging. Begin with tabular supervised; extend to time-series,
anomaly/clustering, frozen text embeddings and small fine-tuning individually.
Remote RunnerAdapter preserves the same lease/result/artifact contracts. Transfer
policy explicitly controls data/labels/secrets, bytes, cost and shutdown. Sealed
assessment remains local when feasible; a trusted remote evaluator requires its
own explicit threat model and acceptance gate.

## Task 1: Deep Code Audit & Transition to an "Agent-First" Coding Harness

### 1.1 Audit of the Current M6 Architecture (The Bottlenecks)

Your M6 system has exceptional systems engineering—the Rust SQLite WAL writer thread (`storage.rs`), epoch generation fencing (`core.rs`), single-use `O_CREAT | O_EXCL` sealed test gate (`workflow.py`), and digest-pinned Docker isolation (`sandbox.rs`) are rock-solid. However, **the scientific layer is fighting the agent**:

1. **Hardcoded Recipe Rigidity (`schema_m6.sql` & `workflow.py`)**: Right now, `experiment_dag` enforces a SQL `CHECK` constraint limiting recipes to `'dummy'`, `'linear'`, `'tree'`, and `'hist_boosting'`. 2. **Rigid Python ABC Contracts (`custom/contract.py` & `features.py`)**: Requiring agents to subclass `CustomEstimator` and routing everything through `SplitAwareFeaturePipeline` restricts the agent's coding freedom. 4. **The 5 Open M6 Release Gates**:
* *Gate 1 (Non-File Tool Recovery)*: `recovery.rs` tracks tool outcomes, but side-effecting bash commands lack idempotency markers.
* *Gate 2 (128 MiB Ceiling)*: Only enforced in `execution.rs::submit()`. Direct artifact writes bypass the check.
* *Gate 5 (Memory Certification)*: Polling RSS from the host cannot catch transient allocations inside Python; hard enforcement requires reading container cgroup v2 `memory.peak`.

## Task 3: High-Concurrency Deterministic Architecture (10 Projects $\times$ 5 Workers = 50 Concurrent Sandboxes)

### 3.1 Why 50 Concurrent `docker run` Processes Will Crash the Host

If you run 10 projects concurrently, each executing 5 scripts simultaneously (50 concurrent jobs), your current M6 setup (`--memory 1g --cpus 1` per `docker run`) will attempt to allocate **50 GiB of RAM and 50 CPU cores**, triggering host OOM kills and Docker daemon lockups. Furthermore, spawning 50 cold containers simultaneously causes massive disk I/O thrashing.

### 3.2 Two-Level Resource Broker & Warm Container Worker Pool

Refactor `crates/harness/src/execution.rs` and `sandbox.rs` into a **Resource-Aware Lease Broker** backed by **Warm Container Zygotes**:

```
+-----------------------------------------------------------------------------------+
| HOST HARDWARE PROBER & GLOBAL RESOURCE BROKER (crates/harness/src/broker.rs)      |
| - Detects Total Host Cores (C) & Usable Host RAM (M)                              |
| - Reserves 2 Cores & 2 GiB RAM strictly for Rust Control Plane + OS + SQLite      |
| - Manages Token Buckets: CPU Millicores Pool & Memory MiB Pool                    |
+-----------------------------------------------------------------------------------+
          |                                                       |
          v (Hierarchical DRF: Dominant Resource Fairness)        v
+-----------------------------------+           +-----------------------------------+
| Project 1 (Weight=5, 5 Active)    |   ...     | Project 10 (Weight=5, 5 Active)   |
| - Guaranteed Share: M/10, C/10    |           | - Guaranteed Share: M/10, C/10    |
| - Can burst if Projects 2..9 idle |           | - Preemptible burst leases        |
+-----------------------------------+           +-----------------------------------+
          |                                                       |
          +---------------------------+---------------------------+
                                      v
+-----------------------------------------------------------------------------------+
| WARM SANDBOX POOL (N Long-Lived Pinned Containers, e.g., 1 per Project)           |
| - Container runs a lightweight Rust/Python Zygote Daemon with pre-imported        |
|   numpy, scipy, pandas, sklearn, lightgbm, torch (Copy-on-Write shared RAM!)      |
| - Executes up to 5 concurrent scripts via Linux cgroup v2 sub-slices + namespaces |
+-----------------------------------------------------------------------------------+

```

#### Key Architectural Upgrades for `execution.rs` & `sandbox.rs`:

1. **Shared Memory via Warm Zygote Containers (Massive RAM Savings)**:
* Instead of 50 isolated `docker run` invocations (which duplicate 150 MiB of Python/NumPy/Scikit-Learn shared libraries 50 times = **7.5 GiB wasted RAM**), run **1 warm container per active project** (10 containers total) or a fixed global pool of containers.
* Inside the container, run a tiny preload daemon (`mlrescurix_worker/zygote.py`) that imports `numpy`, `pandas`, `scipy`, and `sklearn` at boot, then uses `os.fork()` inside an isolated sub-directory `/tmp/job-<id>` and drops privileges for each of the 5 concurrent scripts. Because of Linux **Copy-on-Write (CoW)** page sharing, all 5 workers share the exact same physical RAM pages for Python libraries!


2. **Dynamic Resource Token Tagging**:
* Every script execution declares a **Resource Profile** (`MICRO`, `STANDARD`, `HEAVY`):
* `MICRO` (EDA, linting, unit test, preflight check): `250m CPU, 256 MiB RAM, max 15s`.
* `STANDARD` (0.5 fidelity HPO trial, feature engineering): `1000m CPU, 768 MiB RAM, max 120s`.
* `HEAVY` (Full refit, ensemble stacking, small neural fine-tune): `2000m CPU, 2048 MiB RAM, max 600s`.


* The Rust `ResourceBroker` only dispatches a job when `allocated_ram + job.ram <= host_budget_ram` and `allocated_cpu + job.cpu <= host_budget_cpu`. Thus, 10 projects can easily have 50 scripts queued/active—40 lightweight/IO-bound or staged seamlessly across 8–16 physical cores—**with zero risk of host OOM**.


3. **Thread-Over-Subscription Lock (`OMP_NUM_THREADS`)**:
* When running 50 scripts concurrently, OpenBLAS/MKL/OpenMP inside NumPy and Scikit-Learn will default to spawning `num_cpus` threads *per process* (50 $\times$ 8 = 400 threads), grinding the CPU to a halt via context-switching.
* Hardcode in `sandbox.rs` environment injection:
```rust
cmd.env("OMP_NUM_THREADS", assigned_cores.to_string())
   .env("MKL_NUM_THREADS", assigned_cores.to_string())
   .env("OPENBLAS_NUM_THREADS", assigned_cores.to_string())
   .env("NUMEXPR_NUM_THREADS", assigned_cores.to_string())
   .env("POLARS_MAX_THREADS", assigned_cores.to_string());

```




4. **SQLite Reader/Writer Separation (`storage.rs`)**:
* Keep your single dedicated writer thread (`mlrescurix-writer` with `sync_channel(64)`), but add a **Read-Only Connection Pool (`r2d2` or `deadpool-sqlite` with 16 `SQLITE_OPEN_READ_ONLY` connections)** in WAL mode. Dashboard SSE streams, artifact queries, and agent context lookups will never block or contend with the writer thread across 10 concurrent projects.

### 4.2 Hard 64K Token Context Budget & Milestone Compaction Engine (`context.rs`)

To guarantee no agent ever exceeds **64,000 tokens** (and typically operates under **16,000 tokens** for fast, cheap, high-accuracy reasoning), implement a **3-Tier Hierarchical Memory Architecture** in `crates/harness/src/agents/context.rs`:

| Tier | Token Allocation | Contents | Eviction & Compaction Rule |
| --- | --- | --- | --- |
| **Tier 1: Pinned Constitutional Header** | $\le 4,000$ tokens | Problem statement, hardware/latency constraints, dataset schema summary, current `Apex` scorecard, and system prompt. | **Never evicted.** Updated atomically only when a new Apex model is crowned. |
| **Tier 2: Milestone Episodic Memory** | $\le 12,000$ tokens | Structured Markdown summaries of completed milestones (e.g., *M1 EDA Findings*, *M2 Baseline Insights*, *M3 Dead-End Architectures*). | Compacted at every milestone boundary via `compact_milestone()`. Raw tool logs from previous milestones are deleted from context. |
| **Tier 3: Rolling Scratchpad (Current Turn Loop)** | $\le 32,000$ tokens | Active git worktree file tree, last 5 tool calls, and current hypothesis execution trace. | **Hard Ring-Buffer**: Tool outputs (stdout/stderr) are truncated at `2,000 tokens` (head 50 lines + tail 50 lines; full log saved to `artifacts_v2`). At `48,000 total tokens`, automatic mid-milestone compaction triggers. |

#### The Milestone Compaction Protocol (`compact_milestone` in `orchestrator.rs`):

When a sub-agent completes a task (or hits turn 8), it **cannot** return its raw conversation history to the Orchestrator. It must invoke a terminal tool `complete_subtask(structured_report)` containing:

1. `hypothesis_tested`: 1 sentence.
2. `code_artifact_id` & `git_commit_sha`: Exact pointer.
3. `validation_metrics_delta`: e.g., `ROC-AUC: 0.842 -> 0.879 (+0.037), Latency: 4.2ms`.
4. `key_learnings_and_failures`: Max 250 words (what worked, what failed, why).
The Orchestrator appends *only* this 300-token receipt into its Tier 2 memory and discards the sub-agent's 30,000-token scratchpad.

### 4.3 Zero-Token-Waste Crash Recovery & Resume (`recovery.rs`)

To resolve **M6 Release Gate 1** and ensure stopping/resuming a project wastes zero tokens:

1. **Pre-LLM Prompt Hash & Idempotent Turn Ledger**:
* Before sending a request to OpenRouter/DeepSeek, serialize the exact prompt payload, compute `request_sha256`, and write a row in `provider_turn_receipts(status = 'dispatched')`.
* When the response arrives, commit the raw response JSON and token charge to SQLite **before** parsing or executing any tool calls.


2. **Deterministic Tool-Call Checkpointing**:

* If the harness is killed (`SIGINT`/`SIGKILL`) while 3 out of 5 parallel `sandbox_bash` scripts are running:

* The LLM turn is **not** re-billed or re-prompted (the LLM response is already saved in `provider_turn_receipts`).
* Tools 1, 2, and 3 (which already recorded `outcome_sha256`) immediately return their cached outputs from SQLite.

## Task 5: Expanding Beyond Tabular ML — The Resource-Aware Universal ML Harness

Your intuition here is spot on: **the reason local ML harnesses fail when expanding beyond tabular ML is that they blindly try to run a 7B LLM or heavy RL environment on a laptop, hit OOM or a 40-hour training wall, and crash.**

If you add a **Pre-Flight Hardware & Complexity Estimator (`crates/harness/src/estimator.rs` + `estimator` agent)** at the very start of the workflow, MLRescurix becomes a **Universal Resource-Aware ML Harness** covering Tabular, NLP/Small-LLMs, Time-Series, Unsupervised/Anomaly Detection, and Offline RL.

### 5.1 How the Hardware & Complexity Estimator Works (`Step 0`)

Before initializing the research loop, `mlrescurix-harness estimate` runs a deterministic hardware probe (`sysinfo` + GPU/MPS/CUDA detection) combined with a problem statement analyzer:

1. **Hardware Fingerprint**:
* Detects CPU architecture (`arm64` Apple Silicon / `x86_64`), physical cores, available RAM, disk bandwidth, and accelerator memory (e.g., Apple Metal Unified Memory, local NVIDIA VRAM, or CPU-only).


2. **Analytical Compute & Memory Budgeting Formulas**:
* **Tabular / Classical ML**:

$$\text{Peak RAM} \approx 4 \times (N_{\text{rows}} \times N_{\text{cols}} \times 8\text{ bytes}) + \text{Model State}$$


* **Small LLM / Transformer Fine-Tuning (LoRA / QLoRA / DistilBERT / ModernBERT / MicroLM)**:

$$\text{VRAM/RAM}_{\text{QLoRA}} \approx (0.6\text{ bytes} \times P_{\text{params}}) + \text{Activations}(B \times L \times d_{\text{model}}) + \text{LoRA Gradients}$$


* **Wall-Clock Training Time Estimate**:

$$\text{Est. Time (sec)} = \frac{6 \times P_{\text{active}} \times N_{\text{tokens or samples}} \times N_{\text{epochs}}}{\text{Sustained Host FLOPS Utilization}}$$





### 5.2 The 3-Tier Feasibility Negotiation Protocol

When the user submits a problem statement (e.g., *"Fine-tune an LLM for customer support ticket routing with <50ms latency"* or *"Train a policy on offline user interaction logs"*), the Estimator Agent classifies the request into one of three tiers and negotiates with the user **before spending compute**:

| Feasibility Tier | Condition | Harness Action & Smart Alternative Offered to User |
| --- | --- | --- |
| **Tier GREEN (Local Native Execution)** | Fits within $<70\%$ of local RAM/VRAM and $<30\text{ min}$ wall-clock budget. | Proceeds immediately. (e.g., Tabular GBDT/Stacking, Unsupervised IsolationForest/UMAP+HDBSCAN, Offline RL via Fitted Q-Iteration/Decision Transformer on small state spaces, or fine-tuning a 135M–500M parameter encoder/SLM). |
| **Tier YELLOW (Local Proxy / Distilled Alternative)** | Naive model exceeds local hardware (e.g., user asks for a 7B LLM on an 8GB RAM machine), **but the task can be solved within constraints via an architectural pivot**. | **Proposes a Smart Local Pivot:**<br>

<br>1. *Knowledge Distillation / Teacher-Student*: Use API LLM to label/generate synthetic logits on 2,000 rows, then distill into a local `ModernBERT-base`, `TF-IDF + HistGradientBoosting`, or `100M QLoRA` model.<br>

<br>2. *Frozen Embeddings + Tabular Head*: Extract embeddings once using a quantized local ONNX encoder, cache them to disk, and run MLRescurix's tabular ensemble engine on top! |
| **Tier RED (Remote Burst Required)** | Problem fundamentally requires heavy compute (e.g., 8B+ full fine-tuning, large vision backbones, or 10M-row dataset). | Outputs an exact **Compute Deficit Receipt** (*"Requires 24 GiB VRAM and ~1.8 GPU hours; local machine has 8 GiB RAM"*) and offers to switch the `SandboxRunner` execution backend from local Docker to a remote SSH/Cloud GPU container endpoint while keeping the **Rust Control Plane, SQLite state, and Sealed Test Gate strictly on the user's local machine**. |

### 5.3 Generalizing the Evaluators & Bundles Across Modalities

To support non-tabular modalities without breaking your clean architecture, generalize `scientific/workflow.py` and `bundle.rs` around **Task Archetypes**:

1. `tabular_supervised` (Binary, Multiclass, Regression, Ranking — current M6).
2. `tabular_unsupervised` (Anomaly detection, clustering — evaluated via Silhouette, Davies-Bouldin, reconstruction error, plus stability across bootstrap resamples).
3. `text_and_slm` (Classification, extraction, instruction tuning — evaluated via exact match, F1, Rouge/Perplexity, latency per token, exported as quantized ONNX or GGUF/Safetensors + `inference.py`).
4. `sequential_and_rl` (Time-series forecasting & Offline RL / Contextual Bandits — evaluated via temporal backtesting or Doubly Robust Off-Policy Evaluation [OPE] on sealed trajectory logs).

#### 3. Critical Scientific, Security & Recovery Gaps Fixed

* **Process-Isolated K-Fold Cross-Validation for Black-Box CLI Candidates (`P4.2`, `P4.4`, `ARCHITECTURE.md`)**: If `Candidate v2` only exposes `fit --train-path` and `predict --input-path` and is allowed to run K-fold CV internally on `train.csv`, an untrusted candidate script can leak target statistics across folds or fabricate OOF scores. The harness split driver must materialize fold-specific views (`fold_k/train.csv` and feature-only `fold_k/val_features.csv`) and execute `fit`/`predict` per fold in isolated jobs, with the Trusted Evaluator scoring the resulting OOF predictions against sealed `fold_k/val_labels`.
* **Minimum Slice Support & Adaptive Validation Budgeting (`P4.4`, `ARCHITECTURE.md`)**: Returning fine-grained validation slice diagnostics can leak validation labels if slice sizes are tiny (e.g., 1–3 rows). Added a mandatory `min_slice_support` threshold, coarsened validation diagnostics, and an explicit adaptive validation query budget (`max_validation_queries`).
* **In-Sample Memorization Hazard in Model Rescue (`P4.5`, `ARCHITECTURE.md`)**: If a user supplies a pre-trained `legacy_model.pkl` that was originally fitted on rows now present in the validation or sealed test split, evaluating that pickle directly produces leaked metrics. Rescue Mode now distinguishes **Unfitted Code Rescue** (refitted cleanly on `train_split`) from **Pre-Trained Artifact Rescue** (which requires either a clean refit on `train_split` or an explicitly attested disjoint post-training evaluation dataset before it can compete for Apex).
* **Daemon Container Orphan Reaping (`P1.5`, `P3.4`)**: Killing the host Rust process (`SIGKILL`) terminates the `docker run` CLI client but can leave the container running inside the Docker daemon. Added mandatory container labels (`mlrescurix.project`, `mlrescurix.lease_id`, `mlrescurix.epoch`) so startup/recovery explicitly reaps orphaned daemon containers (`docker ps`/`docker rm -f`) before releasing leases.
* **Two-Tier Storage Budget & Two-Tier Artifact Summaries (`P1.3`, `P2.1`, `P5.3`)**: Clarified that P1.3 enforces the `128 MiB` control-plane state ceiling while establishing a separate, explicitly accounted `artifact_cas_bytes` quota before P2/P4 store multi-megabyte models. Separated `index_digest` (`<=512 B` for context-window leaderboard/DAG injection) from `summary_text` (`<=4 KiB` fetched on demand) so 20 artifact summaries cannot silently consume 20,000 tokens of context.

## Keep, revise, defer

**Keep:** agent-authored Python, independent evaluation, resource leases,
artifact-backed transparency, milestone memory, feasibility negotiation and task
adapters. These match the existing product goal and can be added incrementally.

**Revise:**

* Four generic *coding/data* tools are a compact surface, not the entire harness
API. Delegation, completion, status, cancellation and finalization still need
governed control commands. Generic tools must not bypass scheduling, `OutboundFilter`
or scoring.
* Keep `/workspace:ro` (read-only source tree) during `sandbox_exec` by default, with
writable bounded `/scratch:rw` and `/outputs:rw`. All source edits flow through
`workspace_fs` (or a validated staging diff committed via `workspace_fs`). This
prevents arbitrary shell commands from corrupting branch worktrees mid-flight and
makes interrupted `sandbox_exec` calls safely repeatable by clearing `/outputs/<call_id>`.
* A worktree reset cannot undo an external side effect, remote job, SQLite mutation
or consumed holdout. Reconcile by authoritative receipt; retry only isolated
replayable operations. Provider dispatch without a saved response can have an
uncertain billed outcome. Promise reduced duplicate work, not zero waste.
* SHA-256 addresses immutable blobs, not mutable artifact identity. Separate
records, versions, blobs, references and many-to-many lineage. Separate compact
index digests (`<=512 B` for context injection) from detailed summaries (`<=4 KiB`
fetched on demand). Scorecards need evaluator authority; an agent artifact cannot
self-certify official metrics.
* A single `is_apex` column does not enforce one current Apex or explain a Pareto
set. Use a revisioned project selection record pointing to a verified candidate.
* A new local HTTP service needs authentication, project authorization, safe
rendering and cursor replay. Loopback binding alone does not supply these.
* Black-box CLI candidates (`fit`/`predict`) must not be trusted to execute their
own internal K-fold splitting on full training labels without verification, as
buggy or adversarial code can leak target statistics across folds. The harness
split driver must materialize fold-isolated training files and feature-only
validation inputs per fold, scoring fold predictions in the trusted evaluator.
* Hidden validation labels do not prevent repeated-score overfitting or leakage
through fine-grained error slices. Enforce a minimum slice support threshold
(`min_slice_support`), coarsen validation diagnostics, budget adaptive validation
submissions, and preserve an untouched final test. Data agents may inspect
training-split residuals, never row-level sealed validation or test residuals.
* Model rescue (`legacy_model.pkl` or legacy code) must guard against in-sample
memorization: a pre-trained model file may have been trained on rows that overlap
the harness's validation or sealed test split. Official Apex competition requires
either refitting the rescued pipeline from scratch on `train_split` or evaluating
on an explicitly attested, disjoint post-training holdout dataset.
* A 128 MiB total-state ceiling conflicts with large weights/runtime assets and
permanent retry fences. Enforce the current 128 MiB control-state policy first in
P1.3 while defining a separate, explicitly accounted `artifact_cas_bytes` and
`export_bytes` quota before P2/P4 store multi-file model artifacts.
* Ten projects with five scripts each means 50 queued/runnable intents. Fifty
simultaneously running jobs are conditional on admitted resource demand. Memory
limits are caps, not reservations of physical RAM; summed demands are a planning
risk, not proof that container limits allocate 50 GiB immediately.
* Killing the host harness process can orphan running `docker run` containers inside
the Docker daemon. Stamp every container with deterministic labels
(`mlrescurix.project`, `mlrescurix.lease_id`, `mlrescurix.epoch`) so startup and
recovery explicitly reap surviving daemon containers before releasing leases.
* Reserve host/VM capacity by measured capabilities and configurable headroom;
fixed "2 cores + 2 GiB" is unsuitable for every device. Docker's Linux VM budget
can be lower than macOS host RAM. MPS on the host is not exposed merely because
Apple Silicon exists.
* CPU thread settings already exist in one path; apply them to all backends.
Fractional CPU quotas still require at least one library thread and are not an
integer thread allocation. Required resource claims need measurement provenance.
* Context limits include schemas, message overhead and response allowance. Bytes/4
is not a hard token guarantee. Compaction must preserve tool-call/result pairs,
latest steering and pending actions, not merely the earliest 300 request characters.
* Three seeds are configurable repeated runs, not an automatic confidence interval
or proof of generalization. Choose confirmation protocols by task and budget.
* A formula cannot return an exact GPU-hour deficit. Use bounded pilots and report
estimate ranges, confidence and assumptions. Unsupervised internal metrics and
offline RL OPE cannot universally certify downstream usefulness or policy safety.

**Defer:** warm zygote workers, broad remote execution, RL and small-LLM training
until the corresponding capability and scientific acceptance gates pass. Shared
containers enlarge the isolation problem; a child directory and privilege drop
do not establish per-job namespace, process or memory separation.

## External design checks

The following primary sources informed these corrections, accessed 2026-10-14:

* Python 3.13 warns that mixing threads with `fork()` is unsafe. A preloaded
scientific-library daemon therefore needs a dedicated compatibility experiment:
[Python os.fork documentation](https://docs.python.org/3.13/library/os.html#os.fork).
* Cgroup `memory.max` is enforcement; `memory.peak` is measurement of the cgroup
and descendants. A shared container's lifetime peak is not a job-specific
certificate. Kernel/version/reset support must be checked:
[Linux cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html).
* WAL allows reader/writer concurrency, but long readers can prevent checkpoint
completion and grow WAL files. Bound read transactions and size the pool from
measured load rather than hardcoding 16 connections:
[SQLite WAL documentation](https://www.sqlite.org/wal.html).

**Rejected as defaults:**

1. Switching SQLite from FULL to NORMAL while advertising the same crash/power-loss
durability. WAL NORMAL can lose committed transactions on power loss; keep FULL

5. Arrow as guaranteed "zero RAM duplication." Memory mapping can reuse input pages,

benchmark end-to-end peak use. [Arrow memory interfaces](https://arrow.apache.org/docs/python/memory.html).
6. One BPE encoding as exact counting for every provider. Select provider/model
tokenizer and overhead policy; reject unsupported hard guarantees.
7. Universal batch/row equality as proof of zero leakage, universal successful
inference on invalid input, or every ensemble component requiring individually
positive ablation. These are task-specific checks; ensembles can gain jointly.
8. Guaranteed <3 GiB fine-tuning, four-minute training/2.4ms inference, 8–12x search
speedups, <40ms worker startup, or automatic drift-triggered retraining. Preserve
these as proposed experiments, not release promises. Full encoder cost matters.

# Target architecture and contract requirements

Status: proposed implementation contracts, 2026-10-14. Names below are design
targets, not existing commands or generated schemas. Implement versioned schemas
in `contracts/v1/`, run `scripts/generate_contracts.py`, and add cross-language
fixtures in `crates/harness/src/contracts.rs` and `python/src/mlrescurix_worker/protocol/`
in the phase that owns each contract.

## Ownership and flow

```mermaid
flowchart TD
    U[User: problem, data, existing code, constraints] --> I[Intake and feasibility plan]
    I --> O[Lead agent and durable task graph]
    O --> T[Generic tool gateway + OutboundFilter]
    T --> B[Global resource lease broker]
    B --> S[Isolated candidate jobs: /workspace:ro, /scratch:rw, /outputs:rw]
    S --> E[Trusted split driver, evaluator and benchmark runner]
    E --> A[Candidate evidence and Apex selection]
    A --> V[Independent verifier and critic]
    V --> F[Frozen finalization and sealed test]
    F --> D[Standalone deployable bundle]
    T --> R[Artifact registry and event journal]
    E --> R
    R --> UI[Authenticated local 5-view dashboard]
    UI --> C[Revisioned user commands and notes]
    C --> O

```

Rust owns identity, authorization, lifecycle, admission, budgets, durable receipts,
artifact publication, official-result registration, outbound provider sanitization
(`gateway.rs::OutboundFilter`), event ordering and delivery gates. Python owns
data/ML computation and evaluator implementations in an isolated trusted evaluator
scope. Candidate code never shares label access or mutation authority with that
evaluator. Agents own hypotheses and code choices; their claims remain proposals
until deterministic checks accept their evidence.

"Deterministic" applies to state transitions, input binding, receipts and admission.
Model training/LLM reasoning may vary; record seeds, environment/device identities
and numerical tolerances. Identical hashes do not promise cross-device equality.

## Storage budgets and artifact registry

Enforce a two-tier storage reservation contract so artifact growth never starves
control-plane recovery:

1. **Control-Plane State Budget (`control_state_bytes`)**: Enforces the existing
`128 MiB` default cap across SQLite tables, WAL growth, durable tool/provider
receipts, retry fences, checkpoints and emergency recovery headroom.
2. **Managed Artifact & Export Budget (`artifact_cas_bytes` + `export_bytes`)**:
Separately accounted configurable project/global quotas for CAS blobs (weights,
predictions, plots), staged candidate outputs and finalized delivery bundles.
No write path is exempt from reservation accounting.

Use additive migrations from the actual latest schema version (currently 9) and
retain M6 scientific records during transition.

| Entity | Required data and responsibility |
| --- | --- |
| Blob | SHA-256, verified bytes, owned CAS path, media type; immutable content |
| Artifact | Project-scoped logical ID, kind, producer identity/authority, current version, pins, visibility, tombstone |
| Artifact version | Immutable version ID, blob reference, compact `index_digest` (`<=512 B`), bounded `summary_text` (`<=4 KiB`), schema version, source/environment/job bindings |
| Lineage edge | Project-scoped source/destination version IDs and relation: `derived_from`, `evaluates`, `calibrates`, `ensembles`, `packages`, `supersedes` |
| Annotation | User/agent note, author, revision, referenced artifact version; never edits an official score |
| Selection | Project revision, candidate and scorecard version, protocol, rationale; unique current Apex pointer |
| Event | Monotonic cursor, project, type/version, committed revision and bounded payload/reference |

Kinds initially cover data profiles, research notes, code snapshots, run logs/curves,
diagnostic specs, fold/validation predictions, scorecards and Apex bundles. Validate
payloads with versioned kind schemas in `contracts/v1/`; keep extensions namespaced
rather than another permanent SQL enum bottleneck. Directory artifacts use canonical
manifests of file hashes; validate paths, symlinks, file count and aggregate size
before committing.

CRUD means create immutable version, read/query/lineage, update annotations or
publish successor version, and tombstone an unprotected record. Delete never
rewrites lineage, score history, consumed assessments or retry fences. Pinning
controls retention; baseline designation controls comparison; neither crowns Apex.

Publication protocol: acquire byte reservation (from `control_state_bytes` for DB
metadata and `artifact_cas_bytes` for blob bytes) -> write bounded staging -> hash
and fsync -> atomically publish owned bytes -> commit registry plus event -> settle
reservation. Filesystem and SQLite are not one transaction: reconcile staged files,
orphan blobs and incomplete publication receipts on restart. GC marks references
and leases, tombstones, deletes owned unreferenced bytes, then records completion.
Cross-project deduplication must not expose another project's data or retention.

Agents and UI use the same command service. Official scorecards are writeable only
by evaluator authority; claimed agent metrics are explicitly unofficial. List and
leaderboard queries inject `index_digest` (`<=512 B` / ~120 tokens) so multi-item
digests stay compact; full `summary_text` (`<=4 KiB`) and bounded raw log slices
require explicit read calls. `OutboundFilter` redaction policy applies before
notes, summaries or tool outputs enter provider views.

## Coding tools, fold isolation and candidate boundary

Expose four versioned tool families, backed by existing operations where possible:

| Tool | Contract |
| --- | --- |
| `workspace_fs` | Scoped read/write/patch/glob/search in the branch worktree; expected content hash for mutations; bounded results; reject path and symlink escapes |
| `sandbox_exec` | Prefer structured `argv`; explicit shell mode for agent scripts; approved digest-pinned environment (`docker/scientific/image.ref` or locked profile), task generation, lease, deadline, `/workspace:ro`, bounded `/scratch:rw` and `/outputs:rw` caps, durable receipt |
| `evaluate_submission` | Trigger harness-managed fold/validation execution and score bound prediction artifacts against locked metric/split; trusted validation and benchmark receipts; adaptive-query budget (`max_validation_queries`) and minimum slice support (`min_slice_support`) |
| `artifact_crud` | Project-scoped publication/query/version/lineage/pin/tombstone; expected revision and reservation; no official-score forgery |

Keep governed orchestration controls: delegate, inspect status, complete subtask,
pause/cancel/resume, steering and request finalization. No sandbox tool may run
directly without a broker lease. Retain registered project tools as optional
reusable descriptors calling the same gateway rather than an independent runner.

Candidate v2 is an executable directory plus manifest (`candidate/manifest.json`).
The manifest binds source tree hash, training environment lock, inference environment
lock, input/output schemas, task type, supported operations, optional hyperparameter
search space (`search/adapter.py`), seeds and declared resource request:

```text
candidate/manifest.json
candidate/entrypoint.py
candidate/source/...
training.lock
inference.lock

```

```sh
python -m candidate.entrypoint fit --train-path /inputs/train.csv --model-dir /outputs/model
python -m candidate.entrypoint predict --input-path /inputs/features.csv --model-dir /inputs/model --output-path /outputs/predictions.csv

```

**Sandbox Mount & Isolation Contract**:

* During `sandbox_exec` and candidate `fit`/`predict`, the branch source workspace
is mounted **read-only (`/workspace:ro`)**, while per-job `/scratch:rw` and
`/outputs:rw` are mounted writable with strict byte quotas. Code mutations happen
exclusively through `workspace_fs` (or via an explicit copy-on-write staging mode
whose diff is validated and committed through `workspace_fs` on exit).
* Never mount shared control state, evaluator labels, other branches, credentials
or the Docker socket inside candidate containers.

**Harness-Owned Fold Isolation, Calibration & Ensembling**:

* An untrusted candidate script must not be relied upon to partition its own K-fold
cross-validation on full training data, because it could fit preprocessors globally
or leak validation fold labels into OOF predictions.
* Instead, the **Trusted Split Driver** materializes immutable fold-specific training
splits (`/inputs/folds/fold_k/train.csv`) and feature-only validation splits
(`/inputs/folds/fold_k/val_features.csv`) using the locked split strategy
(stratified, grouped, or temporal). Each fold executes `fit` and `predict` in
isolated candidate runs that never see `fold_k/val_labels`.
* Standardized prediction tables (`row_id`, `pred`, `prob_<class_0>...`) bound to
the candidate/model/split hash are scored by the **Trusted Evaluator** and can be
consumed directly by the harness's trusted `calibration.py` and `ensemble.py`
modules without importing untrusted candidate classes into the evaluator process.
* Validation diagnostics returned to agents enforce `min_slice_support` (e.g., at
least 20 rows or 5% of the validation split) and coarsened metrics so agents
cannot reconstruct individual validation labels from small error slices.

**Model Rescue Provenance Boundary**:

* Legacy models and `.pkl` files are untrusted code and must only be inspected or
loaded inside the candidate sandbox.
* Rescue tasks distinguish **Unfitted Code Rescue** (legacy code repaired and refitted
cleanly on `train_split`) from **Pre-Trained Artifact Rescue** (weights fitted
prior to harness intake). Because a pre-trained pickle may have memorized rows in
`val_split` or `final_test`, it is recorded as an `unverified_legacy_baseline`
unless it is either refitted cleanly on `train_split` or evaluated against an
explicitly attested, disjoint post-training holdout dataset.

## Resource broker and execution

Lease fields: project/task/job, generation, backend and device, container label ID,
CPU millicores, library threads, memory limit/reservation, accelerator units/bytes
where supported, scratch/output bytes, PID cap, deadline, heartbeat and environment
hash. Persist reserve/start/finish/reconcile transitions; terminate and reap
containers in the Docker daemon (`docker rm -f` by `mlrescurix.lease_id` label)
before releasing lease capacity.

Use capacity accounting for instantaneous CPU/RAM/GPU/storage and cumulative
accounting for time/tokens/cost. Start with weighted fair queues, per-project limits
and aging; add dominant-resource fairness only when multi-resource traces justify
its complexity. Suspend new admissions under pressure. Do not kill a training job
for fairness unless it explicitly supports resumable checkpoint/preemption.

Available capacity is the constrained runner/device budget minus configurable
headroom, warm-worker overhead and active reservations. Docker VM limits matter on
macOS. `MICRO`/`STANDARD`/`HEAVY` are configurable request presets, not universal
truth. Fractional CPU jobs normally use one library thread; integral leases cap BLAS,
OpenMP, Polars and estimator-specific jobs. Nested CV/HPO parallelism shares the
same allocation. Fifty jobs can queue; actual dispatch satisfies aggregate limits.

Backend capability reports distinguish enforcement, telemetry and certification.
Record per-job `memory.max`/`memory.peak`/`memory.events` and measurement scope on
supported Linux cgroups. An OOM is a failed trial; missing measurements cannot pass
a required constraint. Training peak, inference peak and warm worker overhead are
separate. Metrics collector is trusted and candidate-write-protected. Initially
retain one disposable container per job; pooling is a later measured optimization.

## Durable agents, recovery and memory

Default roles: lead, data/diagnostics, experiment engineer, independent verifier,
critic. Estimator combines deterministic hardware/pilot evidence with agent task
interpretation. Specialist roles are capabilities, not five always-running LLMs.
Keep deterministic verifier separate from an advisory/binding-policy critic.

Task contract: goal, falsifiable hypothesis, immutable inputs, allowed tools,
branch ownership, limits, expected artifacts, acceptance criteria and dependency
IDs. Completion receipt: verdict, experiment/candidate/source IDs, measured metric
delta and protocol, failures, bounded learnings and next actions. Enforce receipt
schema before updating the lead's memory. Invoke research/critic specialists only
when uncertainty or a milestone justifies their cost. External research requires
approved egress and content provenance; training remains offline.

Provider turn ledger binds canonical request, model/settings, prompt/policy/tool
versions, dispatch identity, raw response and usage settlement. Persist the response
before executing tools. Crash before response persistence may leave unknown billing;
reconcile provider evidence when available and refuse to claim exactly-once billing.

Classify tools: pure read, transactional command, isolated replayable job
(including `/workspace:ro` `sandbox_exec` runs writing to `/outputs/<call_id>`),
reconcilable external operation, irreversible operation. Store intent before effects
and result before context update. Unknown outcomes reconcile using job/command/blob
receipts; never reset-and-replay arbitrary shell effects on a writable worktree.
Finalization stays tied to its original frozen artifact; exposed assessment cannot
be recreated by retry.

Pause stops admission and checkpoints at a safe boundary. Cancel fences tasks and
terminates descendants (including labeled Docker containers); restart discovers
surviving containers/processes and leases. Resume loads authoritative state and the
unfinished operation, not a reconstructed conversation guess. Latest steering
changes intent revision and invalidates stale worker proposals. Lost workers,
paused projects and failed projects remain distinct.

Context policy: default approximately 16K total window when supported; maximum
64,000 or provider's smaller window. Count system/messages/schemas/tool results plus
response allowance. Suggested upper-window allocations: 4K pinned state, 12K bounded
milestone summaries (using `<=512 B` `index_digest` entries for leaderboard/DAG
tables), 32K active work, 8K response, 8K schemas/overhead/safety margin. Unused
portions are optional capacity, not required padding. Trigger compaction before the
next request exceeds its budget. Use exact tokenizer where available; otherwise a
conservative bound and an explicit unsupported hard-guarantee report.

Preserve full constraints, newest user steering, Apex/protocol identity, current
leases/tool pairs, unresolved failures and final-test status. Full logs live in
artifacts; provide bounded excerpts and IDs. Summaries are cached with input hashes,
versioned and recoverable; they are never official scientific evidence.

## API and transparent dashboard

Serve loopback Rust API and static UI. Preserve authentication, Host/Origin checks,
CSRF protection for cookie-authenticated mutations, expected revision and idempotent
command IDs. Reuse current `/v1` contracts or add explicit version negotiation;
avoid an accidental `/api/v1` break. Stream durable events after commit with SSE
cursor IDs and `Last-Event-ID` replay. Snapshot includes revision and cursor; expired
cursors trigger a new snapshot. Disconnect slow readers without blocking writers.
Transient telemetry can be coalesced; terminal state/selection events remain durable.

Five views (four project views plus one global/project resource drawer):

1. **Experiment DAG**: actual queued, screening, running, pruned, failed and verified
states with parent/child lineage.
2. **Leaderboard & Pareto view**: validated candidates, feasibility status, pre-trained
rescue baselines and Pareto alternatives across metric, latency and size.
3. **Data & Model Diagnostics**: distribution profiles, calibration curves and
coarsened error slices (`min_slice_support`) with sample counts and provenance.
4. **Research Feed & Code Diffs**: hypothesis, code snapshots, evidence receipts and
critic notes.
5. **Resource & Lease Drawer**: allocated vs measured CPU/RAM, active worker slots,
queue wait times, backend capacity and contention across projects.

Animation follows receipts, never invents progress or hides waiting for resources.
Use accessible status text, reduced-motion support, virtualization and safe markdown
rendering. Treat plot specs as data; reject executable JS/HTML and remote loads.

User notes/edits become revisioned artifacts/commands. Agents receive a bounded
steering delta at safe boundaries after passing `OutboundFilter`. Downloads verify
authorization and immutable manifest identity. Readers use bounded snapshots/
transactions, not a transaction held open for the lifetime of an SSE connection.

## Delivery and expansion

Freeze candidate, environment, selection and approvals; refit within reserved budget;
reload and certify the exact pipeline; consume sealed test once; package matching
weights, inference CLI/API, schemas, locks, training source, scorecard, model card,
lineage and verification receipts. An optional container/service recipe follows;
live hosting is separately authorized. No final verified label for missing evidence.

`TaskAdapter` specifies input/schema/split protocol, fit/predict/evaluate operations,
constraints and packaging. Begin with tabular supervised; extend to time-series,
anomaly/clustering, frozen text embeddings and small fine-tuning individually.
Remote `RunnerAdapter` preserves the same lease/result/artifact contracts. Transfer
policy explicitly controls data/labels/secrets, bytes, cost and shutdown. Sealed
assessment remains local when feasible; a trusted remote evaluator requires its
own explicit threat model and acceptance gate.

# Architecture decision register

Initial proposed defaults, 2026-10-14. These are planning decisions, not claims of
implementation or irrevocable user approvals. Record reversals with evidence.

| ID | Decision | Reason / revisit trigger |
| --- | --- | --- |
| D01 | Repair safety prerequisites before new runtime surfaces | M6 recovery/storage/release gates remain open |
| D02 | Preserve Rust control plane and Docker-only candidate execution initially | Existing isolation requirement; native runtime is a separately certified backend |
| D03 | Keep shared SQLite WAL with FULL durability and converge writes | Cross-project leases and retry fences need durable atomicity; shard only after measured contention and cross-DB recovery design |
| D04 | Immutable blobs/versions, mutable annotations and revisioned selection | CRUD must preserve evidence and distinguish pin/baseline/Apex |
| D05 | Four core coding tool families plus governed controls and optional conveniences | Small generic surface without losing delegation/evaluation/finalization authority |
| D06 | CLI executable contract beside legacy class adapter | Support arbitrary ML/legacy repair without a new universal Python ABC bottleneck |
| D07 | Disposable container per job first; warm pools later | Prove isolation/accounting before optimizing import latency |
| D08 | Capacity-driven dispatch, weighted queues before DRF | 10x5 is a workload/cap scenario, not a minimum hardware guarantee |
| D09 | Keep ~16K economical default with <=64K complete-window cap | Larger windows increase cost; tokenizer must match provider |
| D10 | Replay only known safe operations with full input identities | Resetting files cannot reverse arbitrary effects; zero waste is not guaranteed |
| D11 | Best-first/multi-fidelity default, optional measured MCTS | Search strategy should earn complexity through matched experiments |
| D12 | Deterministic evaluator and independent advisory critic | An LLM does not own official scoring or prove zero leakage |
| D13 | Capability-scoped modality expansion | Local resources and evaluation validity vary by task/backend |
| D14 | Embedded trusted runtime remains; locked optional environments added | Source-independent installs and optional libraries are compatible |
| D15 | Keep `/workspace:ro` during `sandbox_exec`; route source edits via `workspace_fs` | Preserves `SandboxRunner` read-only workspace invariant and makes interrupted `sandbox_exec` calls safely repeatable by clearing `/outputs/<call_id>` |
| D16 | Harness-owned K-fold split driver, `min_slice_support` and validation query budget | Prevents untrusted CLI candidates from leaking across CV folds or reconstructing validation labels from tiny diagnostic slices |
| D17 | Distinguish unfitted code rescue from pre-trained pickle rescue | Prevents pre-trained legacy pickles from claiming Apex via in-sample memorization of validation/test splits without a clean refit or attested disjoint holdout |

## Resolve in the owning phase (with recommended initial defaults)

* P1: exact control-state/archive/artifact/environment/export quotas and emergency
headroom. **Recommended default:** preserve `128 MiB` for `control_state_bytes`
(SQLite, WAL, receipts, fences) and add a configurable `2 GiB` per-project
`artifact_cas_bytes` + `export_bytes` quota, with every write path accounted.
* P2: kind schema extension/visibility policy in `contracts/v1/`, `<=512 B`
`index_digest` vs. `<=4 KiB` `summary_text` bounds, event retention, reader pool

* P3: effective Docker VM capacity probing, container lease labels (`mlrescurix.lease_id`)

* P4: prediction wire format (`row_id`, `pred`, `prob_<class>...`), `argv` vs. shell
surface, binding `sandbox_exec` to digest-pinned `docker/scientific/image.ref`,
adaptive validation query budget (**recommended default:** `max_validation_queries = 50`
full evaluations per session, `min_slice_support = max(20, 5% of val rows)`),
and dataset query restrictions (deny external file readers/extensions/network via
container boundary).
* P5: provider tokenizers, `OutboundFilter` rules for new tool/note surfaces,
summary bounds, prompt versions and search strategy.
* P6: UI framework and packaging for the 5-view dashboard, loopback session
lifecycle and safe artifact renderer.
* P7: safe-export support per family, calibration/ensemble v2 packaging, and target
benchmark protocol.
* P8/P9: estimate calibration, remote data policy, licensed weights, accelerator
backends and thresholds for enabling optimization experiments.

Do not choose per-project databases, weaken fsync, expose a host Python fallback
or remove branch ownership locks based only on a blueprint's throughput claims.
